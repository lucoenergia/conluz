# Liquibase conventions

Read this before writing or changing any database migration. The changelogs live in `src/main/resources/db/liquibase/`.

## Files and changesets

- **One changeset per file**, under `changelogs/`. The changeset `id` equals the file name without extension, in `snake_case` describing the change (for example `add_disabled_at_to_users`).
- **Author:** the maintainer's name, as in the existing changesets.
- **Use the XSD version** the recent changesets use.
- **Append** every new file to `db.changelog-main.xml` with an explicit `<include>`, after the last one. Never reorder includes.
- **Never edit a changeset that has been released.** Liquibase stores its checksum, and editing it breaks every database that already ran it. Fix or extend it with a new changeset.

## Contents of a changeset

- **A header comment** that explains why the change exists, cites the issue number, and states what NULL means for every nullable column it adds. It never refers to internal planning (phases, epics, milestones): issue numbers only.
- **`remarks` on every table and column** it creates, describing what is stored, not why.
- **Preconditions with `onFail="HALT"`** that check the state the changeset assumes (`tableExists`, `columnExists`, `sqlCheck`). When a precondition can fail on real data, its `onFailMessage` includes the query that lists the offending rows.
- **An explicit `<rollback>`.** If the change cannot be undone (for example, a data normalisation), the rollback is empty and a comment says why.

## Common patterns

- **Adding a NOT NULL column to a table with data** takes three changesets:
    1. add the column as nullable;
    2. backfill it;
    3. add the NOT NULL constraint, with a precondition that no row is NULL.
- **Backfills:**
    - guard against overwriting: a precondition checks that no row already has a value;
    - `now()` gives one instant for the whole changeset;
    - when treating "blank" text as empty, spell out the characters (space, tab, LF, CR, FF, VT) instead of `\s`, so the SQL and the Java code agree.
- **Instants** are `TIMESTAMPTZ`, mapped to `Instant`. **Identifiers** are `UUID`.
- **Constraint and index names:** `<table>_<column>_pk`, `_fk`, `_uq`, `_idx`.
- **A foreign key** always states its `ON DELETE` behaviour when it is not the default, and the header comment says why.

## Tests

Every migration has an integration test built on `LiquibaseTestSupport`, following the latest migration tests:
1. apply up to the changeset before the new one;
2. seed rows that cover the cases the migration must handle;
3. apply the rest and assert the result;
4. check that every precondition that can fail halts with its message, and applies nothing;
5. roll back, check that the schema is as before, and apply again.

Migration tests seed raw rows on purpose: they test the schema at a point where the application code does not apply.

## Documentation

After a schema change, regenerate the ER documentation in `docs/db/er/` from a database migrated with the real changelog:
- `conluz_db.sql` with `pg_dump --schema-only --no-owner --no-privileges`;
- `conluz_db.dbml` with `@dbml/cli db2dbml`, fixing by hand the partial, expression and exclusion indexes it mangles;
- `conluz_db.png` cannot be regenerated by an agent: say so in the PR description.

## Pull request

The PR description has an **Upgrade actions** section. A migration that runs automatically on startup needs none: write "None".
